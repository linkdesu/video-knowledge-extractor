# 智能语义分块：停止增长后整段划主题，窗口只约束提示词

整理切片原本严格按固定时长切「整理分块」（`chunkMinutes`，默认 10 分钟），每个分块各自走一遍主题分析。主题由模型按时间区间给出，不受分块边界约束，于是一个跨越边界的话题会被切成两个半截主题：观众看到两条相近标题、内容各占一半。这个话题在原视频里是完整的，被切开的唯一原因是分块边界。

改法不是把分块做大，而是把「排队粒度」和「提示词粒度」分开：排队粒度为整段，提示词粒度按窗口。

## Status

已接受（accepted，2026-11-07，r96）。

## 决定

1. **项目级开关「智能语义分块」**（`semanticChunking`，默认开启）。开启时停止增长的文件按整段分析，关闭时退回固定时长分块；旧 `projects.json` 没有该字段时按开启处理。开关只影响以后产生的分块，已在队列里的任务不重排。
2. **停止增长才整段**（`GROWTH_IDLE_SECONDS`，严格超过 30 秒）。文件还在增长时仍按满块入队：等「整段」意味着录制期间零产出，这与「持续整理中」的可见性冲突。停止增长后，剩余未处理区间一次性入队一个分析任务，`cursorSeconds` 直接推到文件时长。
3. **窗口只决定提示词大小。** `analyzeVideoRange` 收到一个整段区间后，内部按 `TOPIC_WINDOW_SECONDS`（600 秒）切成连续窗口喂给既有 `segmentTopics`：逐窗产候选主题，再用既有的 `segment-merge` 提示词把所有候选合并。被窗口边界切开的话题由合并步骤合回一条主题。窗口不自造边界语义，也不改变主题的时间区间合法性——`sanitizeTopics` 照旧夹取与合并重叠段。整段重排时，已经被分块覆盖的那截不再送模型：只对未覆盖部分划新主题，覆盖段里仍待确认的主题原样交回队列，避免同一段内容被划出第二套近同主题、也避免旧待确认主题从队列里消失。
4. **窗口不写进 `VideoData.chunks`。** `chunks` 承担三件事：精确复用判断、区间重跑的 `refreshOnly` 覆盖判断、断点恢复（`slicedSecondsFrom`），语义单位一律是「分析区间」。把窗口写进去会让精确命中匹配不上、让复用判断被窗口边界污染，也会在调整 `TOPIC_WINDOW_SECONDS` 后与历史数据脱节。区间级记录保持不变。
5. **进度按窗口上报。** `segment-topics` 的 `done/total` 从「1/1」变成「i/窗口数」，分析任务快照带 `progress`，界面据此显示主题分析进度，而不是长时间无反馈。
6. **进度与状态口径不变。** 「已处理」仍是「从开头起连续、全部主题都已切片的分块终点」，「未切片内容时长」仍是时长减去这一段。整段模式下分块数组里只有一个区间，二者公式不变。

## Considered Options

- **重叠窗 + 去重**：窗口重叠能让边界话题在两侧都完整出现，但同一段字幕进两个候选集，必然制造近重复主题，需要再做一次相似度去重。合并提示词已经在做「相近主题是否同一话题」的判断，重叠只会把它的输入变脏。
- **按静音/停顿切窗口**：能避免切在句子中间，但切点仍可能落在话题中间；而「切在话题中间」正是要解决的问题。转写分块（`Chunk`）本身已按停顿切，主题窗口再按停顿切只是把同一个边界换了来源。
- **把分块时长上限调大（例如 60 分钟）**：提示词随视频平方增长，长录屏直接撞上下文上限；也会让录制期的首个分块产出延迟到一个小时。
- **在分块结果之上做后处理拼接**：同一话题被切成两段后，两段的摘要与关键词已各自生成，拼接要靠标题相似度猜；不如让模型在一次合并里看到全部候选。
- **把窗口写进 `chunks`**：见决定 4，会破坏复用与断点恢复的语义。

## 后果

- 长视频的首个主题产出明显变晚（整段转写完才开始划主题）。录制期的按块推进保留这条退路，但已停止增长的长视频只能等整段。
- 同一话题不再出现两条半截主题；主题总数在长视频上可能比按块时更少（跨窗合并），用户确认的工作量下降。
- 候选主题缓存键按窗口行内容计算：窗口方案不变时命中照旧；调整 `TOPIC_WINDOW_SECONDS` 会让长视频的候选缓存整体失效并重算一次（按设计可接受，窗口实现变化本就该重算）。
- 整段任务失败时，重试仍是同一区间（#154 的「原地重排」），不会因为整段粒度而放大失败代价；字幕产物已经在区间级缓存里，重试可以直接复用。
- 关闭开关后行为与 r95 完全一致；术语表新增「智能语义分块」，并在「整理分块」条目里说明开关开启时停止增长的文件不再按时长切块。
