# 导入前音轨可解码预检，以及任务浮层停靠

r42 的 QA 原片是一段加密/损坏的直播录像（`.ts`）：`ffprobe` 给得出 358.9 秒时长、PMT 里也有 AAC 音轨，但几乎每一帧都解不出（实测 `-t 2` 的 `ffmpeg` 以 69 退出，输出 wav 只有 3050 字节）。旧流程先建库、抽封面、发 `prepared`，再抽完整音轨时才失败；用户等了整条抽音时间，看到的还是 `描述` 把 decoder 错误归成「视频文件损坏」，与「重新导出」之间差着一步推断。同一轮 QA 还发现任务浮层 `job-banner` 固定覆盖在卡片底部操作行上，未点「关闭」时点不到「确认主题」。

## Status

已接受（accepted）。新增导入阶段的音轨预检；任务浮层从 fixed 覆盖改为布局内停靠。补充 [ADR-0012](./0012-electron-desktop-utility-process.md) 的 worker 阶段划分与 [ADR-0029](./0029-r35-polish-speaker-merge-and-failure-loop.md) 的失败摘要口径。

## 决定

1. **预检放在 `probeVideo` 之后、`openVideo` 之前。** `packages/core/src/core/audio.ts` 新增 `assertAudioDecodable(videoPath, wavPath)`：用现成的 `extractAudio(..., limitSeconds=2)` 抽 2 秒到 `os.tmpdir()`，无论成败都在 `finally` 删除临时文件。`runExtract` 在探到时长后立刻调用它，因此坏文件不建输出目录、不建缓存目录、不取锁、不发 `prepared`、不进 ASR。
   - 失败判定有两条：`ffmpeg` 非零退出，或 wav 小于 `44 + 8000` 字节（0.25 秒 16 kHz 单声道 pcm_s16le）。后者只兜底「退出 0 但没产出采样」的实现差异，阈值取得比任何有意义的语音片段都短。
   - 抛出的错误是稳定文案 `AUDIO_UNDECODABLE_ERROR`（「音轨无法解码（文件可能已损坏或来自加密直播录像），请重新导出为 mp4/m4a 后再导入」）。ffmpeg 的原始 stderr 只进 `logger().warn("ffmpeg", "音轨预检失败")`，不出现在消息里，避免几十行 `Number of bands ...` 冲到用户面前。
2. **一处文案，两处消费。** 常量在 `audio.ts`，`describeFailure` 直接引用它并返回卡片短原因「音轨无法解码，请重新导出为 mp4/m4a」。重跑一个已登记的旧视频时（main 侧已知 `outputDir`），卡片失败原因因此不再落到「视频文件损坏」；新导入则只有失败浮层，因为条目根本没创建。
3. **不改 `extractAudio` 的失败语义。** 预检只覆盖「开头 2 秒就解不出」。若一段音频前 2 秒正常、之后损坏，仍在转写阶段按原有失败路径处理；不为尚未观察到的文件形态扩大改动面。
4. **浮层改为布局内停靠。** `#root` 改成纵向 flex，`.vn-shell` 用 `flex: 1; min-height: 0` 占满剩余高度，`JobProgress` 外面包一层 `.vn-job-dock`（`flex: 0 0 auto`，右对齐）。浮层不再是 `position: fixed`，内容区 `.vn-content` 的底边就是停靠区的顶边，任何卡片按钮都不可能与浮层相交；关闭后内容区自动恢复满高。

## Considered Options

- **预检放在 `prepared` 之后**：能留下一条失败卡片和短原因，但会为注定失败的文件建目录、抽封面、发一次 prepared。用户在坏文件上看到的仍是一张要手动删除的空卡片。采用更早的失败点，让「无法处理」的文件根本不进库。
- **只靠 `ffprobe` 的 `sample_rate=0` 判定**：这是同一种损坏的常见信号，但不是协议保证；某些容器在 `sample_rate` 正常时载荷已坏，反之也有无采样率信息但可解码的流。用真解码 2 秒，判定依据与后续 ASR 完全一致。
- **把 ffmpeg stderr 拼进错误消息**：诊断价值只在日志里，UI 需要一句可执行的话。stderr 进 `logger()`，消息只留稳定文案。
- **完成后自动收起浮层**：收起会吞掉 r39 约定的终态日志尾部（`job-log-tail` 在完成/失败/取消后仍需可见直到用户点关闭）。停靠保留全部现有行为，只去掉覆盖。
- **给浮层加 `pointer-events: none`**：只放行点击，视觉上仍压着卡片，截图与用户感知的问题没解决。

## 后果

- 坏文件导入的耗时从「整条抽音 + 失败」降到约 0.2 秒（本机实测 Link 原片 182 ms 失败），且不产生任何库条目或缓存目录。
- 干净 `.ts`、mp4、m4a 多花一次 2 秒抽音（约 30 ms 量级），换来的是在进入长任务前发现解码问题；预检成本与第一次抽音同阶。
- 短于 0.25 秒有效采样的音频会被判为不可解码。这类输入本来也无法转写，错误文案会引导用户重新导出。
- 任务浮层打开时会占用约 130–300 px 的内容高度（含日志尾部），库页需要滚动才能看到底部卡片；这是「不覆盖可点区域」的直接代价。终态截图若只要库页，仍可点关闭。
- 预检与失败摘要共用同一个常量，下一轮若改文案，测试、feature 文档与卡片短原因会一起暴露未同步处。
